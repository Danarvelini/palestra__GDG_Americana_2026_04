# User Service — Business Rules

These rules define the **expected behavior** of the User Service API.  
All contributors **must** read this document before submitting or reviewing a PR.

---

## BR-01 · Email Uniqueness

Each user's email address must be **unique** across the system.  
Attempting to register with an already-registered email must return **HTTP 409 Conflict**.

---

## BR-02 · User Roles

The `role` field accepts only the following values: `viewer`, `editor`, `admin`.  
The **default role for every new user is `viewer`**.  
Any value outside the allowed set must be rejected with **HTTP 422 Unprocessable Entity**.

---

## BR-03 · Soft Delete Policy

Users are **never permanently removed** from the database.  
A `DELETE` operation must set `active = False` on the record.  
Inactive users (`active = False`) must be treated as non-existent by **all read endpoints**.

---

## BR-04 · Audit Log

Every **write operation** (create, update, delete) must append a record to the in-memory
`audit_log` list before returning a response.

Each audit record must contain:

| Field       | Description                        |
|-------------|------------------------------------|
| `action`    | `"create"`, `"update"`, or `"delete"` |
| `user_id`   | The ID of the affected user        |
| `timestamp` | ISO-8601 UTC timestamp             |

---

## BR-05 · ID Generation

User IDs must be generated by incrementing the **highest existing ID** in `users_db`:

```python
new_id = max(users_db.keys()) + 1
```

Using `len(users_db) + 1` is **forbidden** — it produces duplicate IDs after any deletion.
